# 代码没改，Agent 的产品承诺为什么变了？

AI 产品经理精选 · 2026-11-18 · 产品落地 / 升级治理

> 独立原创学习整理，不是 Browser Use 官方项目或完整源码。尚未安装、运行或实测；案例、实验与验收阈值均为学习设计，不代表用户已完成项目或取得效果。

## 今日问题

一个替用户完成网页任务的 Agent，昨天还符合预算，升级依赖后，代码没有改，推理方式、成本和等待时间却可能改变。对于需要对客户承诺完成率、预算和响应时间的 AI 产品经理，真正的产品单元不只是代码，还包括依赖版本、默认模型、推理配置与浏览器环境。

今天不再介绍一个框架的功能清单，而是练习：**如何判断一次 Agent 升级是否值得上线，以及如何发现“默认值变化”带来的产品风险？**

- 项目创建于 2024-10-31，不是新项目。本次针对 [1.0.6 发布记录](https://github.com/browser-use/browser-use/releases/tag/1.0.6)，发布时间 2026-11-16 00:51:24 UTC，在本次滚动三个月窗口（2026-08-18 至 2026-11-18）内。
- 维护快照：2026-11-18 仍有推送、未归档。推送日期仅用于维护状态判断，不作为实质创新证据。
- 已核查 [README](https://github.com/browser-use/browser-use/blob/main/README.md) 与 [MIT 许可证](https://github.com/browser-use/browser-use/blob/main/LICENSE)。实际使用时仍需核对依赖、云服务和模型提供方条款，代码许可证不等于服务免费。

## 来源事实与产品推断分开看

**上游事实：**1.0.6 发布记录描述默认模型从 `bu-fast` 转为 `bu-4.0`，并将 reasoning effort 从 medium 改为 high。记录同时提示 Browser Use gateway 的输入/输出 token 单价变化，相关单价为旧默认的 15 倍。

**不可推出的结论：**不能说所有用户的任务总价都上涨 15 倍。模型配置、token 使用量、重试次数、网关路径和任务难度都会影响总账单。上游给出的单任务例子也不构成我们的实测或大样本效果保证。

**本文推断：**只做代码 diff 或接口兼容性检查不够。默认模型变动可能改变延迟、成本、错误分布，甚至用户等待过程中是否需要中断或接管。产品团队应把这些作为升级验收项，而不是把依赖升级当作纯工程维护。

README 建议固定确切版本，并提醒 live-view 链接具有控制浏览器的能力；secret redaction 不是 sandbox。这意味着调试方便和数据边界必须分别设计，不能把“隐藏了密钥”理解为“任务已经隔离”。

## 产品取舍：什么时候该升级？

| 场景 | 更合适的决策 | 需要补的证据 |
| --- | --- | --- |
| 任务复杂、失败后人工补救昂贵 | 可以考虑更强模型 | 完成率增益是否覆盖额外总成本 |
| 高频简单查询、预算严格 | 不要因新版本默认值而被动升级模型 | 显式固定模型后是否满足质量要求 |
| 高风险写操作或涉及真实账号 | 先在隔离测试环境评估 | 授权范围、重复操作与失败恢复证据 |
| 无代表性样本、仅一个漂亮演示 | 暂不扩大流量 | 先定义目标任务与失败类别 |

不适用于用一个样本证明所有网页任务有效，也不用于直接批准金融、医疗等高后果场景。新版本可能修复重要问题，但新不等于对每个产品目标更优。

## 可操作练习：一张升级决策单

以下是**假设的内部测试**，不需要在本仓库开通服务。先用纸面方案和合成数据完成设计；真正执行需另行准备隔离环境、授权和预算。

目标用户：运营同事，每天将公开产品信息整理成草稿。MVP 只读取信息并输出草稿，不自动发送或改写生产数据。

1. 选 30 个代表性任务，包含短页面、分页、缺失字段、页面改版、加载失败。提前写出可人工复核的正确结果，留出 10 个任务作为未参与调优的保留集。
2. 固定浏览器环境、页面快照、提示与最大重试次数。记录每次运行的依赖版本、模型名、reasoning、起止时间、完整费用与人工接管。
3. 在技术上支持时建立四组：旧版本/旧模型、新版本/旧模型、旧版本/新模型、新版本/新模型；reasoning 先固定，之后再单独比较 medium 与 high。若旧版本不支持新模型，明确标注缺失组合，不伪装成完整因果实验。
4. 相同任务各重复 3 次，随机化运行顺序。先看保留集和失败类型，再看平均数；保存异常案例，避免只展示最好的一次。
5. 输出升级结论：上线、有限试用或暂缓。附适用任务、预算上限、监测负责人和可执行的回滚配置。

### 别把评估和缓存的变化算到模型头上

明确写出基线版本。若跨过 [1.0.5](https://github.com/browser-use/browser-use/releases/tag/1.0.5)，还要控制运行结束后的内置评估请求：上游说明它会用运行所用模型发起一次低推理强度的评估，可用 `judge=False` 关闭。若基线早于 [1.0.4](https://github.com/browser-use/browser-use/releases/tag/1.0.4)，截图裁剪与提示缓存行为也可能不同。尽量对齐评估设置和缓存条件，用相同的独立人工评分规则；能拆账时分别记录执行模型、评估和浏览器的成本，不能拆账时不要把差异归因于模型。以上是发布说明与实验设计，不是实测结果。

### 决策单模板

- 用户任务与不做的事：
- 基线版本 / 模型 / reasoning / 浏览器环境：
- 候选配置与明确变化：
- 主指标：独立核验的任务成功率；不得仅凭工具返回成功。
- 约束指标：每个成功任务总成本、P95 延迟、人工接管率。
- 安全约束：未授权写入、越界访问及敏感信息泄漏案例数。
- 当前结果：待测。
- 上线范围与回滚触发条件：

“每个成功任务总成本”应以全部尝试的模型、浏览器和必要人工处理成本，除以成功任务数，不能剔除失败开销后美化单价。零成功时该指标无意义，应直接报告失败。

## 六项验收标准

以下阈值是教学示例，正式使用前按业务损失和预算调整，不是行业标准。

1. 所有运行均能追溯到确切版本和配置；缺少记录则不得用于升级结论。
2. 保留集结果逐项人工核验，完整报告成功数/总数及失败类别。小样本不宣称统计显著或全面胜出。
3. 候选在既定质量底线下，每成功任务总成本与 P95 延迟均不超过预先批准的预算；预算在测试前填写，不能看结果后修改。
4. 页面故障和缺失字段能明确返回不确定状态，不补造事实；测试结果待测。
5. 任一未授权写入、越界访问或敏感信息泄漏即阻止放量，并保存审计记录；零事故样本也不证明绝对安全。
6. 能恢复到明确的旧版本、旧模型和旧 reasoning 配置，并完成一次隔离回滚演练；只回退代码不算完整回滚。

## 风险与边界

- 没有进行本地或云端实测，所有性能与价值判断仍需实验验证。
- 上游默认值及服务价格可能继续变化，实施前需复核发布记录和实际计费渠道。
- 测试网页与真实动态网站存在差异；网页改版、账号状态和地区都可能影响结果。
- live-view 等控制链接应仅限有权限人员使用，不能公开贴入学习仓库；测试使用合成数据与隔离账号。
- 版本固定有助于复现，但长期不升级可能错过修复。应采用定期审查而非永久冻结。
- 更强推理不一定更适合简单任务。真正的产品结论必须连接用户任务与总成本，而不是仅比较模型名称。
